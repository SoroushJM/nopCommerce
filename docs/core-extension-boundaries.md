# مرز تغییرات مستقیم و Plugin

تصمیم کاربر در ۲۰۲۶-۱۰-۱۱: فارسی‌سازی ادمین مجاز است، ولی محل‌های conflict با upstream باید کم شوند. تنظیمات نصب/ایمیل ادمین/PostgreSQL و precompiled views نیز استثناهای تأییدشده‌اند. قابلیت اختصاصی خارج از این استثناها باید در Theme/Plugin بماند.

## کاهش تغییرات مستقیم انجام‌شده

- `Nop.Services/Helpers/WebHelper.cs` و تست بومی آن دقیقاً به `upstream/develop` موجود (`bf60274308`) برگشتند. تغییر پورت به `StorefrontWebHelper` در پلاگین منتقل شد؛ فقط `GetStoreHost` override می‌شود و رفتار پیش‌فرض از base می‌آید. `GetThisPageUrl` و `GetStoreLocation` بومی از همین override استفاده می‌کنند.
- `CommonConfig.HttpPort/HttpsPort` حذف شدند؛ `UsePrecompiledViews` تأییدشده باقی ماند. تنظیم پورت اکنون `StorefrontHostConfig` پلاگین است. startup با Order=3001 پس از ثبت بومی `IWebHelper` در Order=2000 اجرا می‌شود.
- Compose هر دو کلید جدید را می‌فرستد. پلاگین وقتی هیچ پورت جدیدی تنظیم نشده، کلیدهای قبلی environment را می‌پذیرد؛ پورت ناقص جدید با پورت قدیمی ترکیب نمی‌شود. JSON سفارشی باید پیش از اولین اجرا مهاجرت کند؛ ذخیرهٔ config بومی ممکن است کلیدهای حذف‌شدهٔ فایل را قبل از startup پلاگین کنار بگذارد.
- `PersianAdminResourcesStartup` از `Nop.Web` به پلاگین منتقل شد. Order=50 و مسیر بستهٔ ترجمه ثابت‌اند؛ انتخاب culture بومی در Order=100 اجرا می‌شود. نصب/صف انتظار نصب پلاگین شرط کشف این startup است؛ حذف پلاگین، نگهداری بعدی بسته را متوقف می‌کند.
- فیلتر `AdminTransferCalendarAttribute` به پلاگین منتقل و در `MvcOptions` ثبت شد. فقط controllerهای بومی مشتق از `BaseAdminController` را می‌پذیرد؛ public controller و admin controller پلاگین‌های دیگر کنار گذاشته می‌شوند. وضعیت ambient تقویم در `finally` بازگردانده می‌شود. `BaseAdminController` دقیقاً به upstream برگشت.

نصب اولیه از helper بومی استفاده می‌کند؛ `InstallController` redirect تغییر پروتکل ندارد و mapping در مرحلهٔ نصب لازم نیست. پس از نصب و restart، assembly پلاگین نصب‌شده یا در صف نصب کشف می‌شود. برای این کار eager loading دیگری اضافه نشده است.

## PDF و گزارش‌ها: امکان Plugin و هزینهٔ واقعی

بله، `IPdfService` و `IExportManager` قابل جایگزینی از startup پلاگین هستند؛ ثبت جایگزین باید بعد از Order=2000 باشد. XLSX/XML اکنون از فیلتر داخل پلاگین عبور می‌کنند.

PDF بومی در سه مسیر چاپ تکی، خودش `InvoiceDocument`، `ShipmentDocument` و `CatalogDocument` را می‌سازد؛ factory قابل تزریق یا event آماده‌سازی سند ندارد. متدهای چاپ و بخشی از آماده‌سازی آدرس/اقلام/جمع‌ها virtual هستند. پیاده‌سازی کاملاً داخل پلاگین ممکن است، ولی با وضعیت فعلی تقریباً سه workflow ساخت سند و constructor با ۳۲ وابستگی را تکرار می‌کند. این کپی‌ها هنگام upgrade نیازمند مقایسه با upstream خواهند بود؛ حذف diff هسته به‌تنهایی حذف هزینهٔ نگهداری نیست.

به همین دلیل، در این نوبت patchهای کوچک فارسی‌سازی PDF و export تحت استثنای صریح کاربر حفظ شدند. `TransferCalendar` تا وقتی مصرف‌کنندهٔ بومی دارد در Nop.Services باقی می‌ماند؛ انتقالش به پلاگین باعث وابستگی معکوس یا تکرار سرویس می‌شود. این فایل جدید است و هم‌نام upstream ندارد. ادعای انتقال کامل PDF به Plugin مطرح نیست.

برای ادامهٔ کاهش conflict، منطق preference، action تقویم و assetها می‌تواند از نقاط توسعه منتقل شود. patchهای کوچک View برای قرارداد ISO تاریخ و table renderer فقط در صورت وجود جایگزینی ساده و معتبر حذف شوند؛ کپی کامل Viewهای upstream پیش‌فرض نیست. بنابراین فارسی‌سازی فعلی هنوز تماماً از هسته خارج نشده است.

## بررسی‌ها

دو معماری مستقل و یک بازبین تازهٔ `gpt-6.1-sol/xhigh` نقاط توسعه، ترتیب ثبت سرویس‌ها و شرط‌های فیلتر را بررسی کردند. بررسی‌های مرورگر و عملکرد طبق تصمیم کاربر اجرا نمی‌شوند.

تست‌های پورت قبلی به TUnit منتقل شدند و همان فایل‌های production از طریق source link کامپایل می‌شوند. تست‌ها تغییر پروتکل، همان پروتکل، IPv6، authority بدون پورت، پورت نامرتبط، config نامعتبر، مسیر/query، ترتیب جایگزینی DI، کلیدهای قبلی و config ناقص جدید را بررسی می‌کنند. تست Admin HTTP محافظت‌شده، XML و XLSX را در هر دو تقویم از actionهای بومی دریافت می‌کند؛ این شاهد عبور از فیلتر Plugin و metadata است، نه پذیرش همهٔ محتویات فایل یا ظاهر PDF. منابع/ترجمه‌ها و رفتار فارسی‌سازی PDF تغییر نکرده‌اند.

در ۲۰۲۶-۱۰-۱۲، پروژهٔ TUnit با کد فعلی ساخته شد و ۱۵ سناریوی `StorefrontHostTests` و ۴ سناریوی `AdminTransferPluginTests` روی سرور محلی موفق شدند؛ مجموعاً ۱۹ موفق، صفر شکست و صفر skip. این اجرای هدفمند، تست‌های پورت/config و قرارداد خروجی XML/XLSX را پوشش می‌دهد؛ ادعای اجرای دوبارهٔ کل مجموعه یا پذیرش بصری مطرح نیست.
