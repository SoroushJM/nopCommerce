# توسعهٔ فعلی دو تم فروشگاه

وضعیت ساختار: ۲۰۲۶-۱۰-۱۲، nopCommerce 5.00 و .NET 10. نام نمایشی فروشگاه نوشت‌افزار «مداد رنگی» است؛ شناسهٔ فنی `Madadrang` حفظ شده است. `MishaShop` نام فنی میشا شاپ است و نام نمایشی آن از تنظیم فروشگاه می‌آید.

در ۲۰۲۶-۱۰-۱۵ شناسهٔ قبلی `Boutique` به `MishaShop` تغییر کرد. ورودی قدیمی در build، تنظیم runtime و انتخاب ذخیره‌شدهٔ مشتری/فروشگاه همچنان به نام جدید نگاشت می‌شود. نام `BoutiqueThemeSettings` برای حفظ کلیدهای تنظیمات hero و شناسهٔ سرویس موجود Docker یعنی `boutique` حفظ شده‌اند؛ این تغییر نیازی به انتقال دیتابیس، رسانه یا volumeها ندارد. گزارش‌های QA تاریخی نام زمان اجرای خودشان را نگه می‌دارند.

## پروژه‌ها و مرز مسئولیت

| پروژه | مسئولیت و وابستگی |
| --- | --- |
| `src/Storefront/Storefront.UI.Shared` | قراردادهای نمایشی و تعامل عمومی، محصول و سبد؛ بدون ارجاع به دو برند یا سرویس‌های سرور nopCommerce |
| `src/Storefront/Storefront.UI.Madadrang` | اجزا، استایل و دارایی‌های مداد رنگی؛ وابسته به Shared |
| `src/Storefront/Storefront.UI.MishaShop` | اجزا و استایل تم لباس؛ وابسته به Shared |
| `src/Storefront/Storefront.Client` | میزبان WebAssembly، Shared و برند انتخاب‌شده در ساخت |
| `src/Plugins/Nop.Plugin.Misc.PersianStorefront` | تبدیل مدل‌ها، اتصال به سرویس‌ها و کنترلرهای nopCommerce، تنظیمات و سیاست ورود |
| `src/Presentation/Nop.Web/Themes` | ترکیب قالب MVC، کامپوننت‌ها و نمایش بومی قابلیت‌های فروشگاه |

Shared سرویس مستقل یا دیتابیس ندارد. هر خروجی انتشار نسخهٔ خودش از کد و دارایی‌های لازم را حمل می‌کند. پروژهٔ Preview محیط نمایش اجزا است و جای آزمون فروشگاه واقعی را نمی‌گیرد. تصمیم معماری در [ADR 0004](adr/0004-storefront-ui-libraries.md) ثبت شده است.

## سیاست استقلال ظاهر دو تم

تصمیم تأییدشده در ۲۰۲۶-۱۰-۱۵: ظاهر مداد رنگی و میشا شاپ باید مستقل از یکدیگر باشد؛ اصلاح ظاهر یک تم نباید ظاهر تم دیگر را تغییر دهد. این سیاست هدف اصلاح‌های بعدی است و به معنی حذف وابستگی‌های فعلی به CSS بومی نیست.

- رنگ، فونت، فاصله‌ها، چیدمان و قواعد مخصوص هر برند در پروژه و محدودهٔ همان تم تعریف شوند. اصلاح یک برند با selector سراسری در Shared انجام نشود.
- رفتار، قراردادها و کامپوننت‌های پایهٔ بدون هویت بصری می‌توانند مشترک بمانند؛ ظاهر آن‌ها از تنظیمات و استایل تم میزبان تأمین شود.
- در هر صفحه‌ای که برای اصلاح معرفی می‌شود، تا حد امکان از کامپوننت‌های Blazor Blueprint استفاده شود و وابستگی همان صفحه به استایل‌های پیش‌فرض nopCommerce و overrideهای تکراری کاهش یابد. رفتار خرید، کنترل‌های لازم، RTL و نمایش واکنش‌گرا حفظ شوند؛ این تصمیم مربوط به استایل است، نه جداسازی سرویس‌های فروشگاه.
- تغییر اجزای مشترک از نظر اثر روی هر دو تم بررسی شود؛ اصلاحی که فقط فایل‌های اختصاصی یک تم را تغییر می‌دهد، به‌خودی‌خود نیازمند تغییر تم دیگر نیست.

## انتخاب و اجرای تم

انتخاب ساخت با `StorefrontTheme=Madadrang|MishaShop|All` انجام می‌شود. مقدار پیش‌فرض مخزن `Madadrang` است. `All` فقط برای توسعهٔ هر دو رابط در یک checkout استفاده می‌شود؛ خروجی انتشار هر فروشگاه برند خودش را دارد.

انتخاب اجرا با `StorefrontThemeConfig__Theme=Madadrang|MishaShop` انجام می‌شود. مقدار اجرا باید در خروجی ساخت موجود باشد. این انتخاب، دیتابیس یا پوشهٔ تصاویر را عوض نمی‌کند. اگر انتخاب قالب توسط مشتری در تنظیمات بومی فعال باشد، انتخاب معتبر مشتری همچنان رعایت می‌شود.

برای Visual Studio از [راهنمای پروفایل‌ها](storefront-visualstudio.md) استفاده کنید. فایل launchSettings محلی است؛ نمونهٔ بدون اطلاعات اتصال در `docs/examples/launchSettings.storefront.json` قرار دارد. هنگام استفاده از `All`، پس از تغییر property یک‌بار Rebuild لازم است.

برای اجرای محلی Windows، `start-local.cmd` را دوبارکلیک کنید یا `./scripts/run-storefront.ps1 -Theme Madadrang|MishaShop` را با یکی از دو نام تم اجرا کنید. راه‌انداز، افزونه و وابستگی‌های وب/مرورگر را برای تم انتخابی در Debug می‌سازد و همان تم را با Razor توسعه اجرا می‌کند. پورت‌های پیش‌فرض مداد رنگی و لباس به‌ترتیب `5602` و `5630` هستند و با `-Port` تغییر می‌کنند. راه‌انداز پیش از build، سرور قبلی همین checkout را متوقف می‌کند؛ فرایند checkout دیگری را متوقف نمی‌کند. انتخاب تم همچنان تنظیم اتصال، دیتابیس و رسانه را عوض نمی‌کند؛ برای اجرای همزمان دو نصب مستقل از بسته‌های انتشار استفاده کنید. تنظیمات خصوصی نصب قبلی در کلون تازه وجود ندارند و باید برای همان نصب محلی آماده شوند.

برای ساخت خروجی‌های مستقل:

```powershell
./scripts/publish-storefront.ps1 -Theme Madadrang -Environment test -HttpPort 6240 -HttpsPort 6241
./scripts/publish-storefront.ps1 -Theme MishaShop -Environment test -HttpPort 6250 -HttpsPort 6251
```

این فرمان‌ها بسته می‌سازند؛ سرور یا دیتابیس راه‌اندازی نمی‌کنند. پوشهٔ خروجی باید بیرون checkout باشد. هر نصب به تنظیم خصوصی اتصال، دیتابیس، رسانه، کلیدهای محافظت داده و هویت فرایند/کانتینر خودش نیاز دارد. [راهنمای انتشار](storefront-deployments.md) جزئیات تنظیم هر محیط را نگه می‌دارد. پورت‌های مثال باید آزاد باشند؛ بازهٔ ۱۹۸۶ تا ۲۰۸۵ در این Windows مستثنا شده است.

ورودی‌های مستقل Release از `UseSharedCompilation=false` استفاده می‌کنند و همین انتخاب به فرایند ساخت Client منتقل می‌شود. قالب‌های معتبر در ساخت پیش‌فرض خطای کامپایل تولید کرده بودند؛ ساخت و انتشار کامل هر دو خروجی با این تنظیم موفق شد. علت مربوط به وضعیت کامپایلر مشترک استنباطی است؛ تنظیم عمومی Debug تغییر نکرده است. بسته‌های نهایی و محدودیت اجرای فعلی در [ممیزی تکمیل](qa/storefront-completion-audit.md) ثبت شده‌اند.

## اجرای VS Code و ساخت پیش از F5

تنظیم و بررسی: ۲۰۲۶-۱۰-۱۳. پوشهٔ ریشهٔ مخزن، یعنی `nopCommerce` که `.vscode` و `src` داخل آن هستند، را در VS Code باز کنید. برای نسخهٔ اصلی پروژه، پوشهٔ والد `nopcomerce` یا یکی از worktreeها را انتخاب نکنید. .NET 10 مطابق `global.json`، Node/npm و افزونه‌های Microsoft C# و C# Dev Kit لازم‌اند. تنظیمات `.vscode/settings.json`، فایل `src/NopCommerce.sln` را برای IntelliSense انتخاب می‌کنند و مقدار `StorefrontTheme=All` را به language server می‌دهند.

فایل `src/Presentation/Nop.Web/Properties/launchSettings.json` محلی و خارج از Git است. در checkout تازه، پروفایل‌های [نمونهٔ launchSettings](examples/launchSettings.storefront.json) را با تنظیم محلی خود ادغام کنید؛ مشخصات خصوصی اتصال در این نمونه نیست.

1. برای راه‌اندازی اولیه، `Ctrl+Shift+B` بزنید تا task پیش‌فرض `nop: build solution` کل Solution، از جمله پلاگین‌های دیگر، را بسازد.
2. `F5` بزنید و از فهرست، یکی از پروفایل‌های `Madadrang`، `MishaShop` یا `Nop.Web` را انتخاب کنید. پروفایل‌های دو تم به‌ترتیب روی پورت‌های ۵۶۰۲ و ۵۶۳۰ اجرا می‌شوند.
3. پیش از جابه‌جایی پروفایل یا ساخت دوباره، اجرای دیباگ قبلی را با `Shift+F5` متوقف کنید تا فایل‌های برنامه قفل نباشند.

پیکربندی `nopCommerce: Select Launch Profile` در `.vscode/launch.json`، task با نام `nop: build storefront` را پیش از اجرا فراخوانی می‌کند. این task پروژهٔ `Nop.Plugin.Misc.PersianStorefront` و وابستگی‌های آن، شامل `Nop.Web` و کتابخانه‌های Storefront، را در Debug با `StorefrontTheme=All` می‌سازد؛ ساخت Client و دارایی‌های هر دو تم نیز از target افزونه اجرا می‌شود. نیازی به تغییر پیش‌فرض `Directory.Build.props` برای این مسیر VS Code نیست.

**پس از تغییر پلاگین‌های دیگر، `Ctrl+Shift+B` بزنید.** ساخت F5 پروژه‌های مستقلِ دیگر و پروژه‌های تست را شامل نمی‌شود؛ ممکن است خروجی قبلی آن پلاگین‌ها را اجرا کند. ساخت کامل Solution همچنان task پیش‌فرض است. ساخت تنها `Nop.Web` نیز جای ساخت افزونه و Client را نمی‌گیرد.

### علت کندی و تغییرات اعمال‌شده

مسیر قبلی F5 کل Solution را می‌ساخت. در یکی از اندازه‌گیری‌ها، target پاک‌سازی خروجی پلاگین‌ها (`NopTarget`) ۳۵ بار اجرا شد و حدود ۲۶ ثانیه زمان گرفت، در حالی که مجموع زمان target کامپایل C# (`CoreCompile`) کمتر از یک ثانیه بود. محدودکردن ساخت به افزونهٔ Storefront و وابستگی‌هایش، بررسی پروژه‌ها و پاک‌سازی‌های اضافی را کاهش داد.

ساخت Tailwind در هر دو پروژهٔ `Storefront.UI.Madadrang` و `Storefront.UI.MishaShop` نیز تکرار می‌شد. اگر منابع از CSS جدیدتر بودند ولی محتوای CSS تغییر نمی‌کرد، Tailwind زمان فایل خروجی را به‌روز نمی‌کرد؛ در نتیجه MSBuild در اجرای بعد دوباره همان کار را انجام می‌داد. اکنون `tailwind.stamp` در پوشهٔ میانی ساخت، پایان موفق تولید CSS را ثبت می‌کند و `tailwind.inputs` فهرست منابع را نگه می‌دارد. تغییر، اضافه یا حذف منابع و نبودن CSS همچنان ساخت لازم را فعال می‌کنند؛ در اجرای بدون تغییر، `npm run build` تکرار نمی‌شود.

هر دو task ساخت VS Code از `-maxcpucount:1` استفاده می‌کنند. اجرای موازی با چهار پردازش در این بنچمارک سریع‌تر نبود و نگه داشته نشد. استثنای فشرده‌سازی فایل تنظیم helper محلی FindRazorSourceFile اکنون در `src/Directory.Build.targets` تعریف شده است؛ build ترمینال، IDE و publish تو‌در‌توی Client همگی همان تنظیم را دریافت می‌کنند و به متغیر محیطی اختصاصی task وابسته نیستند. Restore خودکار و ساخت تغییرات همچنان فعال‌اند؛ از `--no-build` استفاده نشده است.

### بنچمارک ساخت، ۲۰۲۶-۱۰-۱۳

اندازه‌گیری روی همین دستگاه Windows با SDK نسخهٔ `10.0.401`، پیکربندی Debug و `StorefrontTheme=All` انجام شد. برای هر حالت دو اجرای متوالی بدون تغییر کد گرفته شد؛ پکیج‌ها قبلاً restore شده بودند و خروجی‌های ساخت موجود بودند. زمان‌ها، مدت کل فرمان CLI ساخت پیش از اجرا هستند و زمان اتصال دیباگر، راه‌اندازی سرور و دیتابیس یا بارگذاری مرورگر را شامل نمی‌شوند. این جدول بنچمارک ساخت سرد یا تضمین زمان کل F5 نیست.

میانگین مرحلهٔ ساخت از حدود ۷۴٫۲ به ۲۷٫۴ ثانیه رسید؛ حدود ۴۶٫۷ ثانیه یا ۶۳٪ کاهش، معادل ۲٫۷ برابر سریع‌تر در این نمونه‌ها. غیرفعال‌کردن Trimming در حالت موازی نیز بهبود نداد و اعمال نشده است. اولین ساخت پس از تغییر فایل‌های پروژه ۴۲٫۴۰۵ ثانیه طول کشید و در میانگین اجراهای بدون تغییر قرار نگرفت.

بررسی نهایی با فرمان واقعی task مربوط به F5 در ۲۸٫۰۰۴ ثانیه تمام شد. ساخت کامل Solution نیز جداگانه در ۹۴٫۱۹۲ ثانیه تأیید شد؛ هر دو بدون هشدار یا خطا بودند. نوسان زمان ساخت کامل را باید هنگام مقایسه در نظر گرفت. تست رفتاری راه‌اندازی برنامه یا خرید، بخشی از این بنچمارک نبود.

برای هر دو تم، رد شدن ساخت بدون تغییر، واکنش به اضافه/ویرایش/حذف فایل Razor، بازسازی CSS حذف‌شده و ساخت با پوشهٔ میانی تازه بررسی شد؛ همه موفق بودند. پس از حذف فایل‌های موقت بررسی، hash فایل‌های CSS به مقدار اولیه برگشت.

گزارش JSON و لاگ‌های این اجرای محلی در `runtime-verification/vscode-build-benchmarks-20261013/` نگهداری می‌شوند؛ این پوشه ignored است و همراه checkout تازه دریافت نمی‌شود. جدول بالا خلاصهٔ ثبت‌شده در مخزن است.

برای تکرار اندازه‌گیری از ریشهٔ مخزن، پس از توقف دیباگ، همان تنظیم محیطی taskها را اعمال کنید. هر فرمان را یک بار برای آماده‌سازی و سپس دو بار بدون تغییر کد اجرا کنید؛ از `Clean` بین نمونه‌های ساخت بدون تغییر استفاده نکنید. `PerformanceSummary` جزئیات targetهای MSBuild را به لاگ اضافه می‌کند:

```powershell

# ساخت کامل؛ معادل مسیر Ctrl+Shift+B
dotnet build src/NopCommerce.sln --configuration Debug -p:StorefrontTheme=All -maxcpucount:1 --verbosity minimal -clp:PerformanceSummary

# ساخت محدود؛ معادل مرحلهٔ پیش از اجرای F5
dotnet build src/Plugins/Nop.Plugin.Misc.PersianStorefront/Nop.Plugin.Misc.PersianStorefront.csproj --configuration Debug -p:StorefrontTheme=All -maxcpucount:1 --verbosity minimal -clp:PerformanceSummary
```

این دو فرمان وضعیت فعلیِ پس از اصلاح Tailwind را می‌سنجند؛ بازتولید اعداد baseline قدیمی به نسخهٔ پیش از آن اصلاح نیاز دارد. برای مقایسهٔ دقیق‌تر، زمان کل فرمان را نیز ثبت کنید؛ خلاصهٔ MSBuild لزوماً همهٔ زمان شروع فرایند را در بر نمی‌گیرد و زمان targetهای تو‌در‌تو را نباید با هم جمع کرد.

### انتشار incremental کلاینت در Debug

بررسی تکمیلی ۲۰۲۶-۱۰-۱۳ در worktree مستقل روی کامیت `ce3024646d` انجام شد تا تغییرات هم‌زمان UI در checkout اصلی وارد بنچمارک نشوند. تنظیمات VS Code و helper محلی FindRazorSourceFile برای مقایسهٔ ساخت‌های بدون تغییر یکسان بودند. اعداد جدول قبلی مربوط به checkout اصلی و مرحلهٔ قبلی بهینه‌سازی‌اند.

`Nop.Plugin.Misc.PersianStorefront` فایل `Storefront.Client.Publish.targets` را وارد می‌کند. در Debug، انتشار Client فقط وقتی اجرا می‌شود که کد، فایل‌های رابط و دارایی‌ها، فهرست فایل‌ها، تنظیمات پروژه یا restore، نسخهٔ SDK، انتخاب تم یا مسیر خروجی تغییر کرده باشد؛ نبودن یکی از فایل‌های خروجیِ ثبت‌شده نیز انتشار را فعال می‌کند. فایل‌های `obj/storefront-client.inputs`، `obj/storefront-client.outputs` و `obj/storefront-client.stamp` در پروژهٔ پلاگین وضعیت انتشار موفق را نگه می‌دارند. ثبت فهرست ورودی‌ها باعث می‌شود حذف و اضافهٔ فایل هم شناسایی شود.

این وضعیت در پوشهٔ مشترک `obj` نگهداری می‌شود، چون Debug و Release می‌توانند در یک پوشهٔ پلاگین منتشر شوند. Release به‌صورت پیش‌فرض همچنان انتشار کامل را اجرا می‌کند و اعتبار کش قبلی را از بین می‌برد. `Clean` نیز فایل‌های وضعیت را حذف می‌کند. ثبت موفقیت فقط پس از پایان موفق دستور publish انجام می‌شود.

بهینه‌سازی incremental تنظیمات trimming و کامپایل را تغییر نمی‌دهد؛ هنگام معتبر بودن خروجی، اجرای دوبارهٔ همان کار حذف می‌شود. در اصلاح بعدی خطای build مستقیم، آرگومان قدیمی `GenerateCompressedFiles=false` نیز از فرمان انتشار حذف شد تا پیش‌فرض‌های فشرده‌سازی SDK حفظ شوند؛ جزئیات و تست مستقل آن در بخش فشرده‌سازی آمده است. ساخت Tailwind هر دو تم نیز از stamp استفاده می‌کند؛ منابع Razor، فایل‌های CSS زیر `Styles`، فایل واردشدهٔ Shared و تنظیمات npm ورودی‌های آن هستند. با اضافه‌کردن منبع یا import جدید به Tailwind، `TailwindSources` نیز باید آن ورودی را پوشش دهد.

برای انتشار اجباری و عیب‌یابی کش از همان فرمان F5 با property زیر استفاده کنید:

```powershell
dotnet build src/Plugins/Nop.Plugin.Misc.PersianStorefront/Nop.Plugin.Misc.PersianStorefront.csproj --configuration Debug -p:StorefrontTheme=All -p:StorefrontClientIncrementalPublish=false -maxcpucount:1
```

ورودی‌های بیرون از درخت‌های ثبت‌شده را می‌توان با `StorefrontClientPublishAdditionalInputs` معرفی کرد. پس از تغییر ابزار یا ورودی خارجیِ ثبت‌نشده، انتشار اجباری لازم است. کش محلی بر timestamp و فهرست فایل‌ها تکیه دارد؛ تغییر دستی محتوای فایل همراه با حفظ timestamp، قرارداد معمول این ساخت incremental را نقض می‌کند.

بررسی‌های رفتاری روی خروجی واقعی انجام شدند:

- ساخت بدون تغییر، انتشار Client و اجرای Tailwind را رد کرد.
- در مقایسهٔ نهایی، SHA-256 هر ۶۰۳ فایلِ خروجی کش‌شده با انتشار اجباری یکسان بود. این تعداد شامل فایل‌های باقی‌مانده از انتشارهای قبلی همین محیط آزمایشی است؛ این تغییر سیاست پاک‌سازی پوشهٔ publish را عوض نمی‌کند.
- حذف CSS منتشرشده باعث انتشار دوباره و بازسازی فایل با همان hash شد.
- اضافه و ویرایش کد C# در Client، WASM منتشرشده را تغییر داد؛ پس از حذف کد آزمایشی، hash فایل WASM به مقدار اولیه برگشت.
- برای هر دو تم، اضافه/ویرایش/حذف Razor و حذف CSS خروجی، ساخت لازم را فعال کردند؛ ساخت بدون تغییر پس از آن رد شد و hash CSS اولیه بازیابی شد.
- جابه‌جایی `All` به `MishaShop`، manifest انتشار را به دارایی‌های تم انتخاب‌شده محدود کرد؛ اجرای تکراری همان تم رد شد و بازگشت به `All` هر دو مجموعهٔ دارایی را برگرداند.
- ساخت پس از `dotnet clean` پلاگین و Client موفق بود. سیاست Release و بی‌اعتبارشدن کش Debug هنگام انتشار بدون کش نیز بررسی شد؛ انتشار کامل Release بخشی از این دور اعتبارسنجی نبود.

برای تکرار بنچمارک، همان فرمان F5 بالا را بدون `StorefrontClientIncrementalPublish=false` اجرا کنید. پس از یک اجرای آماده‌سازی، سه اجرای متوالی بدون تغییر کد و بدون Clean بگیرید؛ مدت کل فرایند را با `System.Diagnostics.Stopwatch` ثبت کنید. برای ساخت پس از Clean، ابتدا `dotnet clean` را با Debug و `StorefrontTheme=All` روی پروژهٔ پلاگین و سپس `src/Storefront/Storefront.Client/Storefront.Client.csproj` اجرا کنید. cache پکیج‌ها و node_modules را در این سناریو نگه دارید.

فایل‌های WASM فعال از manifest همان انتشار انتخاب شدند. دور دوم، نشانه‌های دور اول را در WASM فعال و CSS جایگزین کرد. پس از بازگرداندن هر پنج فایل منبع، hash هر پنج خروجی فعالِ بررسی‌شده و فایل‌های منبع دقیقاً به مقدار پیش از آزمایش برگشت. فایل‌های دارای fingerprint مربوط به انتشارهای قدیمی ممکن است طبق رفتار موجود SDK در پوشه بمانند؛ بررسی روی خروجی فعال انجام شد.

ساخت دور اول 35.786 ثانیه، دور دوم 37.714 ثانیه و ساخت پس از بازگرداندن منابع 41.083 ثانیه طول کشید. ساخت بدون تغییر بعدی 13.215 ثانیه بود و انتشار Client را رد کرد. همهٔ این چهار ساخت بدون هشدار و خطا موفق شدند. شواهد در `real-output-evidence.json`، مقایسهٔ hashهای اولیه و نهایی در `real-output-result.json` و اسکریپت آزمایش در `verify-real-output.ps1` ثبت شده‌اند.

لاگ‌ها و زمان‌های خام آزمایش اولیه در `runtime-verification/build-under20/` در worktree آزمایشی هستند. این پوشه ignored است. نسخهٔ قابل تکرار تست‌ها اکنون داخل مخزن قرار دارد و روش اجرای آن در بخش بعد آمده است. اجرای برنامه، اتصال به دیتابیس و آزمون مرورگر بخشی از این بنچمارک ساخت نبودند.

### اسکریپت‌های بررسی کش و ادغام در checkout اصلی

تغییرات انتشار incremental و ورودی‌های Tailwind در checkout اصلی نیز ادغام شدند. targetهای جدید Tailwind پنل مدیریت، ورودی‌های Razor اضافه‌شده و `native-select.js` نسخهٔ جاری حفظ شدند. تنظیمات اجرای برنامه و بهینه‌سازی‌های runtime تغییر نکردند.

ورودی اصلی تست‌ها [`scripts/test-storefront-incremental.ps1`](../scripts/test-storefront-incremental.ps1) است. دو helper در [`scripts/build-tests/`](../scripts/build-tests/) تست خروجی، تغییر منابع، استایل و انتخاب تم را اجرا می‌کنند. PowerShell 7، SDK پروژه، Node/npm و دسترسی لازم برای restore باید آماده باشند. فرمان‌ها را از ریشهٔ checkout اجرا کنید؛ هنگام تست، برنامه را متوقف کنید و هم‌زمان منابع همان checkout را ویرایش نکنید.

```powershell
# یک ساخت آماده‌سازی و سه ساخت کامل برای اندازه‌گیری زمان
pwsh -File ./scripts/test-storefront-incremental.ps1 -Suite Benchmark -Runs 3

# بررسی SHA-256 خروجی کش‌شده در برابر انتشار اجباری و بازسازی فایل حذف‌شده
pwsh -File ./scripts/test-storefront-incremental.ps1 -Suite Output

# همهٔ سناریوها؛ فقط در worktree ایزوله‌ای که همین تغییرات را دارد
pwsh -File ./scripts/test-storefront-incremental.ps1 -Suite All -Runs 3
```

| Suite | بررسی |
| --- | --- |
| `Benchmark` | یک آماده‌سازی و تعداد `Runs` ساخت کامل؛ ثبت زمان و exit code |
| `Output` | ردشدن انتشار بدون تغییر، برابری SHA-256 همهٔ خروجی‌ها با انتشار اجباری، بازسازی CSS حذف‌شده |
| `Source` | اضافه/ویرایش/حذف C# و تغییر WASM فعال؛ بازگشت hash اصلی |
| `Styles` | هر دو تم: بدون تغییر، اضافه/ویرایش/حذف Razor، حذف CSS و بازسازی آن |
| `Theme` | جابه‌جایی `All` و `MishaShop`، بررسی manifest و ردشدن انتشار تکراری |
| `RealOutput` | دو دور تغییر پنج فایل واقعی و خواندن نشانه‌ها در WASM، CSS و JavaScript؛ سپس بازیابی منابع و خروجی‌ها |
| `All` | اجرای تمام سناریوهای بالا |

اسکریپت، suiteهای تغییردهندهٔ منبع را در checkout اصلی مسدود می‌کند؛ آن‌ها به linked worktree نیاز دارند تا تغییرات هم‌زمان توسعه‌دهنده بازنویسی نشوند. فایل‌های منبع در `finally` با بایت‌های اصلی بازیابی می‌شوند. در صورت شکست suite تغییردهندهٔ منبع، wrapper برای بازیابی خروجی نیز build اجرا می‌کند. بستن اجباری فرایند یا خاموشی سیستم اجرای `finally` را تضمین نمی‌کند؛ برای `RealOutput` نسخهٔ پشتیبان پنج فایل در پوشهٔ گزارش نگهداری می‌شود. تست `Theme` خروجی انتخاب تم را تغییر می‌دهد و در مسیر موفق به `All` برمی‌گرداند.

هر اجرا پوشهٔ مستقلی با نام `runtime-verification/incremental-tests-<timestamp>-<id>/` می‌سازد. `result.json` موفقیت، suiteهای تکمیل‌شده و علت شکست را ثبت می‌کند؛ `build-times.json` زمان ساخت‌های کامل را نگه می‌دارد. لاگ هر مرحله، زمان‌های helperها و در تست واقعی `real-output-evidence.json` و `real-output-result.json` نیز همان‌جا ذخیره می‌شوند. شکست build یا assertion باعث خروج ناموفق اسکریپت می‌شود. اسکریپت‌ها دیگر استثنای فشرده‌سازی را به محیط تزریق نمی‌کنند؛ همان تنظیم مشترک پروژه را آزمایش می‌کنند.

در نخستین اجرای ادغام‌شده، ساخت آماده‌سازی و اجرای بعدی موفق بودند، اما منابع UI هم‌زمان تغییر کردند و اجرای بعدی ناموفق و لاگ آن ناتمام شد. این اجرا بنچمارک «بدون تغییر» محسوب نمی‌شود؛ اعداد ۱۲ تا ۱۳ ثانیهٔ بالا متعلق به worktree ثابت آزمایشی هستند و تضمین زمان checkout در حال ویرایش نیستند.

نسخهٔ مخزنی اسکریپت با `-Suite All -Runs 2` در worktree ثابت نیز به‌طور کامل موفق شد: شش suite خروجی، منبع، استایل، تم، پنج فایل واقعی و بنچمارک تکمیل شدند. برابری خروجی اجباری و کش‌شده برای ۶۲۷ فایل بررسی شد؛ دو ساخت پایانی 13.857 و 14.368 ثانیه بودند. نتیجه در `runtime-verification/incremental-tests-20261013-120904-f6289f/result.json` همان worktree ثبت شده است. این دور پیش از اصلاح مشترک فشرده‌سازی بخش بعد انجام شد.

### رفع خطای build مستقیم و حفظ فشرده‌سازی publish

فرمان `dotnet build NopCommerce.sln` از پوشهٔ `src` در publish تو‌در‌توی Client با `MSB4018 / ApplyCompressionNegotiation` و پیام `Endpoints not found for compressed asset: FindRazorSourceFileConfig.json.gz` شکست می‌خورد. تست‌ها و taskهای قدیمی VS Code متغیر محیطی مخصوصی داشتند که این اختلاف با ترمینال را پنهان می‌کرد.

در `src/Directory.Build.targets`، هنگام فعال‌بودن FindRazorSourceFile فقط `**/FindRazorSourceFileConfig.json` به `CompressionExcludePatterns` موجود اضافه می‌شود. این فایل توسعه endpoint انتشار ندارد. فشرده‌سازی دارایی‌های برنامه فعال می‌ماند. تعریف تکراری از taskهای VS Code و اسکریپت‌ها حذف شد. Release همچنان FindRazorSourceFile را غیرفعال می‌کند.

آرگومان `GenerateCompressedFiles=false` از publish پلاگین حذف شد. targets نصب‌شدهٔ SDK `10.0.401` برای Static Web Assets از `CompressionEnabled` و `PublishCompressionFormats` استفاده می‌کنند؛ پیش‌فرض انتشار، Gzip و Brotli است. وجود آرگومان قدیمی به‌تنهایی نشانهٔ خاموش‌شدن فشرده‌سازی در این SDK نبود.

تست قابل تکرار [`scripts/test-storefront-compression.ps1`](../scripts/test-storefront-compression.ps1) تنظیمات مؤثر SDK را می‌خواند و Client را در Debug و Release با `StorefrontTheme=All` به پوشه‌های تازه منتشر می‌کند. برای تمام فایل‌های WASM و JavaScript زیر `_framework`، وجود هر دو نسخهٔ `.gz` و `.br` را بررسی می‌کند، آن‌ها را باز می‌کند و SHA-256 محتوای بازشده را با فایل اصلی مقایسه می‌کند. همچنین نبودن فایل فشردهٔ تنظیم helper و خطای endpoint را بررسی می‌کند. پوشهٔ تازه مانع قبول‌شدن تست با فایل‌های باقی‌ماندهٔ انتشار قبلی می‌شود.

```powershell
# از ریشهٔ checkout؛ build مستقیم Solution و سپس تست publish هر دو پیکربندی
pwsh -File ./scripts/test-storefront-compression.ps1 -BuildSolution

# فقط تست publish، بدون ساخت کل Solution
pwsh -File ./scripts/test-storefront-compression.ps1
```

این اسکریپت دو متغیر محیطی `CompressionExcludePatterns` و `GenerateCompressedFiles` را فقط در فرایند خودش موقتاً پاک و در پایان بازیابی می‌کند؛ اصلاح باید بدون تنظیم کمکی محیط کار کند. نتیجه، لاگ‌ها، تنظیمات مؤثر، تعداد فایل‌ها و حجم هر فرمت در `runtime-verification/compression-tests-<timestamp>-<id>/` ثبت می‌شوند. این تست ساخت و محتوای بستهٔ انتشار را تأیید می‌کند؛ ارسال واقعی `Content-Encoding` از سرور یا CDN به مرورگر نیاز به آزمون HTTP جداگانه دارد.

اعتبارسنجی ۲۰۲۶-۱۰-۱۳ پس از اصلاح، روی checkout اصلی:

- همان `dotnet build NopCommerce.sln` از `src` بدون متغیر کمکی در 266.947 ثانیه موفق شد؛ صفر خطا و یک هشدار موجود `CS0108` در `EuropaCheckVatService/Reference.cs`. این ساخت کل Solution است و زمان آن معیار ساخت گرم F5 نیست. لاگ در `runtime-verification/compression-fix/solution-build.log` ثبت شد.
- publish تازهٔ Debug در 30.498 ثانیه و Release در 29.762 ثانیه موفق شدند. تمام نسخه‌های فشردهٔ زیر پس از بازشدن hash برابر با فایل اصلی داشتند. نتیجهٔ کامل در `runtime-verification/compression-tests-20261013-123837-ad70d6/result.json` ثبت شد.

| پیکربندی | فایل اصلی WASM/JS | نسخهٔ فشردهٔ بررسی‌شده | حجم اصلی، بایت | Gzip، بایت | Brotli، بایت |
| --- | ---: | ---: | ---: | ---: | ---: |
| Debug | 76 | 152 | 18,103,567 | 6,749,284 | 5,142,821 |
| Release | 75 | 150 | 17,534,946 | 6,548,143 | 4,967,488 |

حجم‌های جدول فقط فایل‌های WASM و JavaScript زیر `_framework` هستند؛ اندازهٔ کل سایت یا اندازه‌گیری انتقال واقعی مرورگر نیستند.

## رفتار و قابلیت‌های بومی

صفحات از مسیر MVC بومی nopCommerce می‌آیند. اجزای تعاملی مداد رنگی HTML اولیه را با `WebAssemblyPrerendered` تولید می‌کنند و سپس در مرورگر فعال می‌شوند. پرداخت، قیمت، موجودی و سبد به سرویس‌های سرور متکی‌اند؛ state مرورگر مرجع مبالغ خرید نیست.

بوتیک نمایش کامل بومی محصول را نگه می‌دارد. در مداد رنگی فقط مدل‌هایی که شرط صریح `NativeProductPresentation.Supports` را دارند از محصول مشترک استفاده می‌کنند؛ فرم‌های فایل، متن، کارت هدیه، اجاره، قیمت واردشده توسط مشتری و دیگر موارد پوشش‌داده‌نشده به نمایش کامل بومی برمی‌گردند. مسیرهای بومی جست‌وجوی پیشرفته، سبد، wishlist، مقایسه، حساب و checkout محفوظ‌اند. رابط مشترک سبد خلاصهٔ محاسبه‌شدهٔ سرور را مصرف می‌کند.

لینک‌های قدیمی محصول/سبد به مسیر بومی متصل یا redirect می‌شوند. مرور کل کاتالوگ از مدل جست‌وجوی استاندارد، مرتب‌سازی و صفحه‌بندی سرور استفاده می‌کند؛ محدودیت فیلترکردن یک مجموعهٔ ۲۰۰تایی در Client متعلق به نسخهٔ قدیمی است. جست‌وجوی پیشرفتهٔ دسته/تولیدکننده/فروشنده/توضیح/برچسب به مسیر بومی Search ارسال می‌شود.

[نقشهٔ قابلیت‌ها](storefront-feature-coverage.md) حفظ منبع را از تأیید عملکرد جدا می‌کند. پشتیبانی بومی یا موفقیت build به‌تنهایی تأیید گردش خرید و افزونهٔ نصب‌شده نیست.

## استایل، عکس و ترجمه

هر برند Tailwind و دارایی‌های خودش را دارد؛ Blueprint و اجزای عمومی از Shared مصرف می‌شوند. CSS پایهٔ DefaultClean در لایهٔ `native` وارد می‌شود تا کنترل‌های بومی قابل استفاده بمانند و reset بدون لایه، utilityهای تم را نپوشاند. [گزارش اصلاح cascade](qa/storefront-native-css-layer.md) شامل محدودیت بررسی جاری است.

نام، لوگو و عکس hero بوتیک از داده‌ها و تنظیمات بومی خوانده می‌شوند. seed نمونه در `scripts/BoutiqueQaSeed` فقط به کپی مشخص آزمایشی بوتیک محدود است؛ تصاویر آن تصویرسازی لباس بدون مدل انسانی هستند. اسکریپت قابل استفادهٔ عمومی روی فروشگاه واقعی نیست و قیمت/تصویر محصولات موجود را با تغییر manifest بازنویسی نمی‌کند.

بستهٔ عمومی فارسی در اسمبلی افزونه قرار می‌گیرد تا volume قدیمی App_Data آن را پنهان نکند؛ نسخهٔ فایل برای میزبان‌های بدون resource، fallback است. واردکردن عمومی missing-only است و ترجمه‌های فعلی فروشگاه را بازنویسی نمی‌کند. [راهنمای ترجمه](storefront-public-localization.md) پوشش منبع و محدودیت دادهٔ موجود را توضیح می‌دهد.

عنوان‌های اصلی محصول، سبد، حساب، کاتالوگ، فیلتر و منوی مشترک از منابع بومی زبان فعال آماده می‌شوند. قرارداد `NativeUiLabels` فقط متن و جهت را به Client می‌دهد؛ direction پنل‌های Blueprint و قالب MVC نیز از زبان فعال می‌آید. محتوای معرفی برند و نمونه‌های فارسی دادهٔ فروشگاه است. بررسی مستقیم ۱۷ مورد HtmlRenderer، حفظ مقادیر فرم، محدودیت قیمت و RTL/LTR را تأیید کرد؛ تعامل پنل در مرورگر هنوز به اجرای بستهٔ تازه وابسته است.

## ورود، بررسی و فرمت‌بندی

OTP نمونه فقط برای سیاست مجاز مداد رنگی در Development با زبان فارسی است و پیامک واقعی ارسال نمی‌کند. مسیر بومی ورود مدیر/مشتری موجود است؛ بوتیک و زبان‌های دیگر از ورود بومی استفاده می‌کنند. موفقیت mock به معنی آمادگی ورود پیامکی محیط واقعی نیست.

تست‌های بدون سرور Shared در `Storefront.Theme.Tests` و قراردادهای منبع در `Nop.Storefront.Tests` هستند. تست HTTP به URL صریح کپی ایزوله نیاز دارد؛ helper بومی پورت ۵۰۹۰ را رد می‌کند. [دستور بررسی دو تم](../src/Tests/Storefront.Theme.Tests/RUNTIME-QA.md) و [ممیزی تست‌های بومی](storefront-native-test-audit.md) پیش‌نیازها و تفاوت assertionهای قدیمی را توضیح می‌دهند.

فرمت C# با `scripts/format-storefront.ps1 -Verify` روی افزونه، سه کتابخانهٔ رابط، Client و Preview بررسی می‌شود. این فرمان ممکن است diagnosticهای موجود را گزارش کند؛ اجراشدن آن به معنی موفقیت قبلی همهٔ فایل‌ها نیست. قالب Razor از formatter رسمی ویرایشگر استفاده می‌کند. سوابق دقیق در [گزارش فرمت‌بندی](storefront-formatting.md) هستند.

[ممیزی تکمیل](qa/storefront-completion-audit.md) وضعیت اجرای بسته‌ها و بررسی‌های هنوز انجام‌نشده را ثبت می‌کند. راهنمای نسخهٔ نخست و گزارش ۲۰۲۶-۱۰-۰۳ سند تاریخی‌اند و شاهد تأیید تم جدید محسوب نمی‌شوند.
