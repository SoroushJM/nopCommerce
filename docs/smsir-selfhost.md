# ورود پیامکی و استقرار فروشگاه‌ها

افزونهٔ `Sms.SmsIr` ارسال قالب Verify در sms.ir را به ورود مشترک مدادرنگی و میشا وصل می‌کند. تنظیمات از پنل ادمین، بخش SMS providers و گزینهٔ Configure افزونه قابل تغییر است. مسیر مستقیم: `/Admin/SmsIr/Configure`.

## تنظیمات ادمین

- API key در دیتابیس با سرویس رمزنگاری nopCommerce ذخیره می‌شود. مقدار آن در HTML برگردانده نمی‌شود؛ خالی‌گذاشتن کادر هنگام ذخیره، کلید قبلی را حفظ می‌کند.
- Sandbox: فقط در Development اجازهٔ ارسال درخواست آزمایشی و نمایش کد وجود دارد. کلید باید از نوع Sandbox حساب sms.ir باشد. قالب آماده `123456` و پارامتر `CODE` است. گزینهٔ Sandbox نوع کلید را تغییر نمی‌دهد و از پاسخ ارسال نمی‌توان نوع کلید را تشخیص داد؛ با کلید عملیاتی امکان ارسال واقعی وجود دارد. فقط کلید مخصوص Sandbox ارسال را در خود سرویس شبیه‌سازی می‌کند.
- Production: حالت Sandbox را خاموش کنید و کلید عملیاتی، شناسهٔ قالب تأییدشده و نام پارامتر بدون `#` را وارد کنید. اعتبار واقعی اتصال و قالب هنگام درخواست ارسال بررسی می‌شود، نه صرف ذخیرهٔ فرم.
- شماره خط، اختیاری و فقط برای قرارداد متن عمومی `ISmsProvider` است. ورود فروشگاه همیشه کد را ساختاریافته به Verify می‌فرستد و از متن ترجمه‌شده کد استخراج نمی‌کند.
- تا تکمیل تنظیمات، هشدار بالای داشبورد مدیر مجاز و در System Warnings نمایش داده می‌شود. در Production همراه Sandbox، ورود پیامکی غیرفعال می‌ماند ولی ادمین برای تکمیل تنظیمات در دسترس است.
- وضعیت غیرمحرمانهٔ تنظیمات هنگام شروع برنامه و ذخیرهٔ فرم در `App_Data/smsir-runtime-status.json` نوشته می‌شود. استقرار اول بدون کلید، با هشدار راه‌اندازی ادامه می‌یابد؛ اگر کلید ذخیره‌شده قابل رمزگشایی نباشد یا تنظیمات موجود در محیط مقصد قابل استفاده نباشند، بررسی deployment ناموفق می‌شود. این بررسی ساختار و رمزگشایی تنظیمات است؛ معتبر بودن کلید نزد سرویس هنگام درخواست ارسال مشخص می‌شود.

## گزارش ادمین

در نسخهٔ ۵ nopCommerce این پروژه، تنظیم و انتخاب SMS provider بومی است؛ تاریخچهٔ پیامک و فهرست مسدودی اختصاصی وجود ندارد. گزارش جدید داخل همان افزونه و منوی کنار «SMS providers»، در `/Admin/SmsIr/Reports` قرار دارد و از مجوز بومی مدیریت تنظیمات SMS استفاده می‌کند.

شماره، درخواست‌کننده، زمان UTC، نوع OTP/Text، شناسهٔ قالب، نتیجهٔ درخواست و شناسهٔ پیام نگهداری می‌شوند. کد ورود، متن پیام و API key ثبت نمی‌شوند. فیلتر شماره و وضعیت، صفحه‌بندی و تعداد درخواست‌ها به تفکیک شماره وجود دارد. Sandbox، پذیرش عملیاتی، شکست قطعی، محدودیت محلی و نتیجهٔ نامشخص جدا هستند؛ قطع ارتباط بعد از POST ممکن است نتیجه را نامشخص بگذارد و ارسال خودکار تکرار نمی‌شود.

دکمهٔ «استعلام تحویل» برای پیام عملیاتی دارای شناسه، گزارش همان پیام را از sms.ir دریافت می‌کند. پذیرش پیام به معنی تحویل نیست. طبق [مرجع رسمی sms.ir](https://sms.ir/rest-api/)، نتیجهٔ تحویل ۷، خطای ارسال ۱۱۵ و شناسهٔ صفر در پاسخ Bulk، مسیرهای متفاوت اعلام لیست سیاه هستند. این نتیجه‌ها در فیلتر لیست سیاه سرویس دیده می‌شوند؛ فهرست دائمی ممنوعیت شماره در فروشگاه ایجاد نمی‌شود. وضعیت تحویل قبلی در پاسخ ناقص حفظ می‌شود. کلید Sandbox امکان استعلام واقعی تحویل ندارد.

محدودیت‌های مهمان، IP و شماره با دلیل و زمان پایان جدا ثبت می‌شوند. محدودیت مهمان/IP به معنی مسدودی سراسری شماره نیست. درخواست‌های مسدود تکراری یک شماره با دلیل و زمان پایان یکسان، همراه شمارنده و آخرین درخواست‌کننده در یک رکورد تجمیع می‌شوند. داده‌های گزارش از زمان نصب افزونه جمع می‌شوند و در دیتابیس پایدارند.

## شماره و کد یک‌بارمصرف

ورودی `0912…`، `+98912…`، `0098912…` و ارقام فارسی/عربی به شناسهٔ `+98912…` تبدیل می‌شوند. شماره‌های جدید در `Customer.Phone` با این قالب ذخیره می‌شوند. چند شکل رایج شماره‌های توسعهٔ قبلی نیز هنگام lookup بررسی می‌شوند؛ چند حساب منطبق یا حساب مسدود/حذف‌شده، ورود را متوقف می‌کند. هیچ حسابی خودکار ادغام، حذف یا دوباره فعال نمی‌شود. ورود مدیر از مسیر بومی `/login` باقی است.

hash و salt کد، زمان انقضا و تلاش‌ها در گروه اختصاصی `StorefrontOtp` جدول بومی GenericAttribute نگهداری می‌شوند. عمر کد دو دقیقه، سقف بررسی پنج تلاش، فاصلهٔ درخواست یک دقیقه، سقف هر شماره پنج درخواست در پانزده دقیقه و سقف IP بیست درخواست در ساعت است. ارسال ناموفق هم سهمیه مصرف می‌کند؛ retry خودکار HTTP انجام نمی‌شود. کد پس از موفقیت مصرف می‌شود. حالت فعلی یک فرایند برنامه در هر فروشگاه است؛ اجرای چند replica نیازمند قفل توزیع‌شده است.

## اجرای محلی و seed

کلید خصوصی خارج از Git در `%LOCALAPPDATA%/MadadrangDev/smsir-local.json` قرار می‌گیرد:

```json
{
  "ApiKey": "your-sandbox-key",
  "Sandbox": true,
  "TemplateId": 123456,
  "CodeParameterName": "CODE"
}
```

```powershell
./scripts/run-storefront.ps1 -Theme Madadrang -Port 5602
# برای رابط میشا از -Theme MishaShop استفاده کنید.
./scripts/seed-storefront.ps1 -BaseUrl http://localhost:5602
```

launcher هر دو پلاگین را می‌سازد و پیش از شروع برنامه فقط پلاگین‌های نصب‌نشده را در صف نصب استاندارد قرار می‌دهد. نصب واقعی با nopCommerce انجام می‌شود. تنظیمات فایل خصوصی فقط در Development و در صورت نبود کلید ذخیره‌شده وارد می‌شوند؛ تنظیمات ادمین بازنویسی نمی‌شوند. خود seed پیامک نمی‌فرستد. seed روی برنامه‌ای که از قبل اجراست، در صورت صف‌شدن نصب، درخواست restart و اجرای مجدد می‌دهد. `-AdminOnly` رفتار قبلی خود را حفظ می‌کند.

هر دو theme در همین checkout محلی از دیتابیس تنظیم‌شده در App_Data استفاده می‌کنند؛ تغییر theme به‌تنهایی دیتابیس توسعهٔ تازه‌ای ایجاد نمی‌کند. جداسازی دیتابیس و فایل‌ها در استقرارهای مستقل زیر برقرار است.

## استقرار از Windows به Linux

PowerShell 7.4+، .NET SDK پروژه، Node/npm، Docker Desktop با engine لینوکسی، OpenSSH `ssh` و `scp` لازم است. روی سرور Docker Compose، Bash، Python 3 و flock لازم‌اند. کلید سرور باید از قبل در known_hosts بررسی و ثبت شده باشد؛ اسکریپت تأیید میزبان را غیرفعال نمی‌کند.

```powershell
./scripts/deploy-madadrang.ps1 `
  -Server server.example -SshUser deploy -SshPort 22 `
  -IdentityFile C:/private/deploy-key `
  -KnownHostsPath C:/private/known_hosts `
  -RemoteRoot /srv/madadrang `
  -EnvironmentFile C:/private/madadrang.env `
  -NonInteractive

./scripts/deploy-mishashop.ps1 -ConfigPath C:/private/misha-deploy.json
```

بدون `-NonInteractive`، مقادیر الزامیِ واردنشده پرسیده می‌شوند. `-ConfigPath` یک JSON خصوصی با کلیدهای `host`, `username`, `port`, `keyFilename`, `knownHostsPath`, `remoteRoot` است؛ مسیر فایل کلید و known_hosts می‌تواند نسبت به فایل تنظیمات باشد. پارامترهای صریح بر تنظیمات فایل اولویت دارند.

اسکریپت از source فعلی snapshot مستقل می‌سازد، برنامه را برای Linux منتشر می‌کند، image را روی Windows می‌سازد، با SCP منتقل و checksum را کنترل می‌کند؛ سپس اسکریپت مشترک Bash را از طریق SSH اجرا می‌کند. رسید در پوشهٔ خصوصی build ذخیره می‌شود. کلید sms.ir وارد image یا فایل‌های انتقال deployment نمی‌شود.

برای هر فروشگاه RemoteRoot مستقل و فایل `.env` مخصوص از `.env.example` بسازید: theme، slug، نام دیتابیس و پورت‌ها متفاوت؛ رمزهای دیتابیس و گواهی یکتا باشند. فایل `.env` فقط بار اول به مقصد منتقل می‌شود؛ دفعات بعد نسخهٔ سرور حفظ می‌شود. اسکریپت روی layout ناشناخته یا پروژهٔ Compose قدیمی، فایل‌ها را خودکار جایگزین نمی‌کند. برای سرور آزمایشی دو فروشگاه با سرویس‌های قدیمی `madadrang`/`boutique`/`database`، مسیر موجود `deploy-storefront.ps1` و فایل تنظیمات خصوصی همان سرور حفظ شده است.

## استقرار روی خود Linux

```bash
bash scripts/deploy-madadrang.sh --build --non-interactive
bash scripts/deploy-mishashop.sh --project-dir /srv/mishashop \
  --image nop-storefront:mishashop-release --archive /tmp/misha-image.tar --non-interactive
```

بدون `--image` یا `--build`، حالت تعاملی نام image آماده را می‌پرسد. اسکریپت theme فایل `.env` را کنترل می‌کند، قفل استقرار می‌گیرد، پیش از ارتقا backup دیتابیس می‌سازد و فقط image سرویس همان پروژه را عوض می‌کند. named volumeهای دیتابیس، App_Data، تصاویر، فایل‌ها و گواهی حذف نمی‌شوند. در شکست آمادگی نسخه، image قبلی برگردانده می‌شود؛ دیتابیس خودکار restore نمی‌شود. override نسخهٔ موفق در `.storefront-releases/current-image.yml` نگهداری می‌شود؛ ارتقاهای بعدی را از همین اسکریپت انجام دهید.

در اولین استقرار، نصب بومی nopCommerce را در مرورگر تکمیل کنید. پس از restart نصب، هر دو افزونه خودکار نصب می‌شوند. registry واقعی و صف نصب بررسی می‌شوند؛ صرف بازبودن پورت به معنی نصب موفق نیست. در محیط واقعی دادهٔ نمونهٔ کاتالوگ ایجاد نمی‌شود. اسکریپت قدیمی `docker/deploy-madadrang.sh --seed-data` برای داده و presentation فروشگاه آزمایشی قبلی حفظ شده است.

## بررسی‌ها

```powershell
dotnet run --project src/Tests/Nop.Storefront.Tests -- --treenode-filter '/*/*/SmsIrTests/*'
pwsh -File scripts/tests/test-smsir-deployment.ps1
python scripts/check-nopcommerce-core.py
```

تست‌های SmsIrTests بدون شبکه و بدون ارسال SMS هستند: قالب درخواست، خطاهای HTTP/سرویس، قالب شماره، ماندگاری challenge بین scopeها، مالکیت مهمان، cooldown، انقضا، قفل تلاش‌ها، replay، عدم افشای کد در Production و برخورد با حساب‌های تکراری/مسدود را بررسی می‌کنند. بررسی بصری هر دو رابط و deployment واقعی روی سرور مقصد مرحلهٔ جداگانه‌ای است؛ اجرای تست‌های واحد معادل تأیید آن‌ها نیست.
